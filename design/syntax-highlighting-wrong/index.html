语法高亮搞错了
    可视化导读 · tonsky

    大家把语法高亮搞错了

    语法高亮是扫描工具，不是圣诞彩灯。全上色之后，眼睛会把五颜六色当成新的底色——于是什么都没被标出来。

    核心论点：颜色要少到能一次记在脑子里；只标稀有且重要的东西。高亮一切，等于把 Linear 里每个任务都标成「最高优先级」。
    改编自 Nikita Prokopov（Niki / tonsky）《I am sorry, but everyone is getting syntax highlighting wrong》，2025-10-15。论证以英文原文为准。Alabaster 用色核对自主题源码。
    01

    圣诞彩灯：全亮 = 没重点

    同一段代码，一种把什么都涂上色，一种只留四色。限时点出指定的函数定义。

    先选全亮或四色，再点「开始找」。点函数定义的名字，点到调用不算。
    • 原文测试：在「什么都亮」的主题里找函数定义，和在克制主题里找，体感差一截。本页把这个测试做成可计时的小游戏。
    • 眼睛会适应高对比的杂色，把它们当成新常态。于是该跳出来的结构，反而沉进背景。
    • 「75% 是变量名和函数调用」是原文的经验判断，不是实测。下面直方图按本页样本现算，标了示意。
    02

    两个查找：你真的在用颜色吗？

    正向：看见颜色，说出类型。反向：要想起「类名是什么颜色」。两样都做不到，主题就只是安慰剂。

    三道小题：颜色→类型、类型→颜色、以及「合上眼睛还记不记得」。
    • 原文把这两件事叫 direct index（颜色→类型）和 reverse lookup（类型→颜色）。
    • 多数彩虹主题的实际功能只剩一句：上了色，大概是合法代码。那不是扫描工具，是安心毯。
    • Alabaster 的赌注：绿紫对调会是灾难——因为你真的记住了。
    03

    颜色预算：四种就够记

    Alabaster 只用四类。点色块，看它们在代码里对应什么。

    点下面的色块，代码里对应 token 会闪。原文四色：绿字符串 / 紫常量 / 黄注释 / 浅蓝顶级定义。
    • VS Code 版 Alabaster 实测：字符串 #448C27，常量 #7A3E9D，顶级定义 #325CC0，标点 #777777。注释在 VS Code 里是砖红 #AA3731，和文章口头说的「黄」不完全一样。
    • Zed 版把文章后半的「背景色块」用上了：注释黄底 #fffab4，字符串绿底 #ebfcd6，定义蓝底 #d6f2ff。
    • GitHub README 重述同一原则：不标关键字、不藏注释、不用粗体斜体、只标解析器能可靠认出的东西。
    04

    该亮什么：稀有，而且重要

    变量和调用到处都是，标了等于没标。勾选开关，代码立刻重画。

    默认关掉 keyword 和 call（以及变量使用）。打开它们，看「重点」怎么被淹没。
    • 原文建议：高亮名字和常量；标点可以压暗；不要高亮语言关键字。if 不重要，后面的条件才重要。
    • 顶级定义能让你迅速看到文件结构；常量常常是逻辑路径的起点。
    • 直方图按当前样本的非空白 token 计数，示意「谁占地方」。
    05

    return vs retunr

    拼错之后颜色变了——你真的看得出来吗？

    左侧是「关键字上色」的主题，右侧是克制主题。先自己找，再点「揭示」。
    • 原文例子：把 return 写成 retunr，颜色从红变成紫。作者说自己看不出来。
    • 彩虹主题里，拼错会「掉出」关键字色，理论上该醒目；可你根本没记住 return 本来是红的。
    • 克制主题两边都是底色，你只能靠读单词。那其实更诚实。
    06

    注释不该藏起来

    灰注释来自按行计酬的年代。好注释是在加信息，该抢眼睛。

    切三种看法：常见的灰、Alabaster 的亮、以及「解释 vs 禁用代码」两套注释。
    • Javadoc 式空壳（作者、日期、一句把方法名重复一遍）确实该灰掉。那是该被忽略的字。
    • 好注释解释代码说不出来的东西。原文的争议句：Comments should be highlighted, not hidden away.
    • 两种注释：解释，和被禁用的代码。多数语言语法上分不开；有约定就用约定（原文举 SQL 的 -- vs /* */）。本页用「像不像代码」做示意分流。
    07

    浅色主题的陷阱：用背景色块救人

    深色谱上色相开得开；压暗以后变泥。浅色主题不是不能鲜艳——把颜色铺成底，而不是字。

    拖亮度看色相带如何塌掉；再对比三种浅色高亮法。原文 70% 开发者偏爱深色主题，文章未给原始调查出处。
    • 浅色主题被迫使用「深色的字」：没有好看的深黄、深青绿。这是色域问题，不是品味问题。
    • 技巧：浅色块当背景，字保持深、对比高。色块面积大，颜色仍然清楚。UI 设计师常用，编辑器里少见。
    • Zed 版 Alabaster 已经这么干了。VS Code 版仍以改字色为主。
    08

    一起做一个主题

    按原文步骤往下剥：去关键字、去变量使用、去调用、压标点、亮注释、合并字符串和数字、按层级旋转颜色。

    拖滑块或点左侧步骤。最后一档会并排 before / after。
    • DIY 终点和成品 Alabaster 略有不同。演示按原文：数字并进绿色，并让函数声明比变量声明更亮。
    • Alabaster 成品把数字留在紫色（常量），定义统一浅蓝。作者说这套原则用了约 8 年。
    • 红色留给波浪线和报错，不要拿去涂注释。
    09

    粗体斜体别用；均匀色相也帮不上

    又一种「再加一层强调」的冲动。科学上均匀的色相，看起来反而更像彼此。

    左边用字体变化代替颜色；右边按原文 OkLab 参数重绘均匀色相（示意）。
    • 原文没见过成功的「只用字体、不用颜色」主题。本页是按这个假设做的示意，不是已有产品。
    • OkLab 参数来自原文：L=0.7473 C=0.1253，色相 0° 起每 45°。明度、彩度锁死后，色相对眼睛几乎没差。
    • 眼睛对明暗差远比对色相差敏感。该利用这件事，而不是用公式把它抹平。
    少到能记住，稀有才上色。高亮是扫描工具——不是把代码打扮成合法的证明。
