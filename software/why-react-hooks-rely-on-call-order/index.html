Hooks 与调用顺序
    软件 · React · API 设计

    为什么 React Hooks 依赖调用顺序？

    React 不知道你的 useState 叫 name 还是 width，它只认「这是第几次调用」。这条规则初看很别扭。这一页把常被提议的几种替代方案逐个跑一遍，看它们在哪里坏掉。

    Hooks 像「函数式 mixin」（functional mixins），用来创建、组合你自己的抽象。要让自定义 Hook 能被随意提取、重复调用、互相嵌套、互相传值，状态的身份最好交给持久的调用索引（persistent call index）：函数调用天然构成一棵树，而树没有钻石问题。[1]
    DDan Abramov

    原文：「Why Do React Hooks Rely on Call Order?」，Dan Abramov，overreacted.io（2018-12-13）。写作时 Hooks 还处于实验阶段的提案期。本页忠实于原文的叙述顺序（引子 → 调用索引 → 八个缺陷 → 结语），代码示例取自原文；页面里另有几处标注为「本页补充」的核对与延伸。

    01

    Hooks 真正的重点：自定义 Hook

    很多人一开始不喜欢 Hooks，又纠结于宣传里的某句话。那 Hooks 背后更大的图景是什么？

    Dan 说，Hooks 像一张要多听几遍才会喜欢上的唱片（原文贴了同一个 Hacker News 用户四天前后态度反转的两条评论截图，本页略去）。读文档时别错过「构建你自己的 Hook」那一页：Hooks 就像函数式 mixin，让你创建和组合自己的抽象。

    Hooks 受过一些前人工作的影响，但在 Sebastian（Sebastian Markbåge）把想法分享给团队之前，Dan 没见过真正类似的东西。这篇文章要解释的，是提案里最有争议的那一点：具体的 API 选择和它解锁的性质之间是什么关系。

    02

    React 只认「第几次调用」

    变量名 name、surname 根本没有传给 React，那重新渲染时，它怎么知道哪份状态归谁？

    学 Hooks 时第一个、也许是最大的冲击：它们依赖重新渲染之间持久的调用索引。这个决定显然有争议，所以 React 团队一反常态，等到文档和演讲足够把它讲清楚之后才公布提案。

    原文的例子是一个表单：三个 useState 加一个 useEffect。数组解构只是给你自己起名；React 把 name 看成「第一个状态变量」，surname 是「第二个」，依此类推。调用索引（call index）给了它们跨渲染的稳定身份。[1][5]

    点「挂载」看首次渲染：每调用一次 Hook，就在组件的链表末尾新建一个格子。再点「setName(…) 后重渲染」：React 只是从头沿着链表一格一格往下读。然后打开「把第 2 个 Hook 放进 if」，再把 name 清空重渲染，看会发生什么。
    本页补充（非原文）：在 React 的实现里，函数组件对应的 fiber 节点用 memoizedState 指向第一个 Hook 对象，每个 Hook 对象再用 next 指向下一个，构成单向链表；渲染时有一个游标沿链表前进（见 React 源码 ReactFiberHooks）。所以把 Hook 放进条件分支，一旦某次渲染跳过了它，后面所有 Hook 都会读到「上一个人的格子」。官方的《Hooks 规则》（Rules of Hooks）因此要求：只在顶层调用 Hook，不要放在条件、循环或嵌套函数里；配套的 eslint-plugin-react-hooks 会检查这一点。开发模式下 React 会警告 Hook 顺序发生变化，调用数变少时会抛出类似「Rendered fewer hooks than expected」的错误。[3][6]

    表面上看，依赖调用索引就是感觉不对。直觉是有用的信号，但也可能误导人，尤其在我们还没完全吃透要解决的问题时。下面 Dan 挑出几种最常被提议的替代设计，展示它们在哪里坏掉。他强调这份清单不求穷尽（他们见过十几到上百种方案，过去五年也一直在思考别的组件 API），各种方案的缺陷往往重叠，所以按缺陷归类。这也不是说 Hooks 完美无缺。

    03

    缺陷一：无法提取自定义 Hook

    如果一个组件只准调用一次 useState，把状态都放进一个对象里，像类组件那样，有什么不好？

    令人意外的是，很多替代方案根本不支持自定义 Hook（custom Hooks），而自定义 Hook 恰恰是这个提案的主要目的。比如有个方案禁止组件多次调用 useState()。Hooks 本身允许把状态放进一个对象，你不必拆成一堆变量；但支持多次调用的意义在于：你可以把一部分有状态逻辑（状态 + effect）提取到自定义 Hook 里，而这个 Hook 也能独立拥有自己的本地状态和 effect。

    两个开关：规则（只准一次 / 允许多次）× 写法（全写在组件里 / 提取出 useWindowWidth()）。四种组合里只有一种不成立。
    04

    缺陷二：名称冲突

    给 useState 传一个字符串 key，显式地给每份状态起名，不就不用依赖顺序了？

    常见建议是让 useState() 接受一个 key（比如字符串），在组件内唯一标识一个状态变量。你大概不会在同一个组件里手滑写两次 useState('name')；但在开发自定义 Hook 时，你很可能要增删状态变量。这样一来，每次给自定义 Hook 加一个状态，都可能弄坏（直接或间接）用到它的组件，因为它们也许已经用了同一个名字。

    这是一个没有「为变化而优化」（optimized for change）的 API：现在的代码看着「优雅」，需求一变就很脆弱。React 的 mixin 当年就吃过这个亏。[1][4][10]

    组件 Form 有自己的 'name'，并用了一个库里的 useCurrentUser()。库作者发布 v2，在 Hook 里新增了一个也叫 'name' 的状态。切换版本和存储方式，在输入框里打字。示意：⚠️ 这不是 React 的 API
    05

    缺陷三：同一个 Hook 不能调用两次

    把字符串换成 Symbol 呢？Symbol 是唯一的，总不会撞了吧？

    「带 key 的 useState」的另一个变体是用 Symbol 之类的东西做 key。提取 useWindowWidth() 时它好像能用：模块顶层放一个 widthKey = Symbol()。但如果要提取输入框处理逻辑 useFormInput()，然后在 Form 里为名和姓各调用一次，就坏了：两次调用都拿同一个 valueKey 去调 useState，等于写了 useState(valueKey) 两遍。（Dan 承认这个 Hook 本身没什么用，但可以想象它像 Formik 那样处理校验、脏标记。）

    真正的 Hooks 没有这个问题，因为每一次调用 useState() 都得到自己隔离的状态。

    06

    缺陷四：钻石问题

    两个自定义 Hook 底层都用了同一个 useSubscription()，按名字存状态会怎样？

    技术上它和缺陷三是同一个问题，但因为太有名，值得单独说：维基百科上有词条，有时被叫作「致命死亡钻石」（deadly diamond of death）。React 自己的 mixin 系统就受过它的害：有时两个 mixin 都正好做你要的事，却因为扩展了同一个「基础」mixin 而互不兼容。[4][7]

    useWindowWidth() 和 useNetworkStatus() 都想在底层用 useSubscription()，这完全合理。自定义 Hook 的作者应该能放心地开始或停止使用另一个自定义 Hook，而不用担心它在调用链某处「已经被用过」。事实上，除非每次改动都审计所有用到你这个 Hook 的组件，否则你永远无法知道整条链。

    「按名字合并」：状态像 mixin、像固定 key 那样按名字存，两条路汇到同一个 useSubscription，形成钻石，底下的 state 和 effect 撞在一起。「按调用顺序」：每次调用都是树上独立的一枝，切过去后点「走一遍」看 React 按什么顺序编号。

    原文的结论只有一句：函数调用没有「钻石」问题，因为它们构成一棵树。

    07

    缺陷五：复制粘贴会弄坏东西

    用闭包给每个 Hook「实例化」出独立的 key，能不能挽救带 key 的方案？

    可以引入某种命名空间，比如用闭包隔离 key：每个自定义 Hook 先通过工厂 createUseFormInput()「实例化」，再在组件里用。这相当笨重：Hooks 的设计目标之一，正是避开高阶组件和 render props 那种深层嵌套的函数式风格。现在任何自定义 Hook 用前都得实例化，而且实例在组件体里只能用恰好一次。每个 Hook 都要写两遍（顶层声明一次、调用处一次），改一点东西也得在两处之间跳；名字也永远有两层：工厂 createUseFormInput 和实例 useNameFormInput、useSurnameFormInput。

    这些问题不是克服不了，但 Dan 认为它们比遵守 Hooks 规则带来更多摩擦。重要的是，它们打破了「复制粘贴」的预期：不加闭包包装直接提取一个 Hook 仍然能用，直到你第二次调用它的那一刻才冲突。一个 API 看起来能用，等你发现链条深处某个冲突后，又逼着你「把所有东西都包起来」，这很糟糕。

    08

    缺陷六：我们仍然需要 linter

    每层自定义 Hook 都把 key 组合下去（'useFormInput(' + key + ').value'），冲突不就没了？那条件调用又意味着什么？

    在各种替代方案里，Dan 最不讨厌这个，但他认为不值得。传了不唯一或拼错的 key 的代码会碰巧能跑，直到某个 Hook 被调用多次或与别的 Hook 撞车；如果它本来就是有条件调用的（我们不就是想「修掉」无条件调用这条要求吗？），冲突可能很久以后才暴露。记得逐层传 key 这件事脆弱到需要 lint 来检查；key 还要在运行时充当键，每个都给包体积添一道小口子。可如果无论如何都要 lint，我们到底解决了什么问题？

    而「有条件地声明状态和 effect」本身的语义就很怪。原文用一个计数器追问：

    提取组件很可能会成为躲开这些困惑的「最佳实践」。所以无论怎么回答，条件声明的语义都怪到你多半想用 lint 禁掉它。既然反正要 lint，「正确组合 key」的要求就成了累赘，它没有换来任何我们想做的事。反过来，去掉这个要求、回到原提案，确实换来了东西：把组件代码复制进自定义 Hook 不需要加命名空间、少了 key 带来的体积小口子、实现还能更高效一点（不需要 Map 查找）。积少成多。

    本页补充（非原文）：后来 React 官方文档确实把「想重置状态就换一个组件，或者给组件换一个 key」写成了推荐做法（React 文档「Preserving and Resetting State」一节）。另外，React 19 新增的 use API 是一个例外：文档明确说它可以在条件和循环里调用，因为它读取的是传入的 Promise 或 Context，并不占用按顺序存放的状态格子。[8]

    缺陷七：Hooks 之间无法传值

    把 Hook 的初始化放进默认参数或装饰器里，看起来更「声明式」，丢掉的是什么？

    Hooks 最好的特性之一，是可以在它们之间传值。原文的例子是一个聊天收件人选择器：useState 的返回值 recipientID 直接传给 useFriendStatus()；换收件人时，这个 Hook 会退订上一位朋友的在线状态、订阅下一位。

    换一个收件人，看值怎样从一个 Hook 流到下一个，以及 effect 发出的订阅 / 退订调用。下面的开关对比同一逻辑在 render props 写法下的「伪层级」。
    原文的第二个例子：React Spring 用 useSpring 做「拖尾」动画，pos2 跟着 pos1，pos3 跟着 pos2。在框里移动鼠标或横向拖动手指（本页用简单的弹簧公式重做，不是 React Spring 本身）。

    如果调用 Hook 不发生在函数体里，你就没法轻松地在它们之间传值、不加很多层组件就变换这些值、用 useMemo() 缓存中间计算，effect 也没法用闭包捕获它们。用约定绕开是可以的，但要你在脑子里「对上」输入和输出，违背了 React 一贯直接的风格。没有 Hooks 时，render props 是最接近的办法，但要拿到全部好处得借助 Component Component 之类，语法噪声大，因为那是一种伪层级（false hierarchy）。Hooks 把这种层级拍平成传值，而函数调用是最简单的传值方式。

    缺陷八：仪式感过重

    把内置 Hook 挂到 this 上、或者作为参数一路传下去，让代码不「隐式依赖」React，划算吗？

    这一类方案大多想避开 Hooks 对 React 的「表面依赖」。Dan 推荐读 Sebastian 回复的第一节「注入模型」（Injection Model）[2]，自己只说一句：程序员更愿意用 try/catch 处理错误，而不是在每个函数间传错误码；更愿意用 ES Modules 的 import（或 CommonJS 的 require），而不是 AMD 那种把 require 传给你的「显式」定义。try/catch、require、React Context 都是同一种务实：即使总体上重视显式，我们也希望有一个「环境式」（ambient）的处理者，而不是把它显式地穿过每一层。Hooks 也一样。

    上：切换几种写法，看「显式」要付出的样板。下：拖动滑块增加自定义 Hook 的嵌套层数，看需要手动穿过多少个参数。

    就像定义组件时我们直接从 React 拿 Component，而不是为每个组件导出一个 createModal(React) 工厂；真要替换 React，在模块系统层面做就行。Sebastian 也提到，技术上可以把从 react 导出的 Hooks「重定向」到别的实现。另一类增加仪式的做法是把 Hooks 做成单子（monadic），或加一个 React.createHook() 之类的一等概念。抛开运行时开销，任何加包装的方案都丢掉了普通函数的一大好处：它们好调试到了极点。你可以用调试器步入步出，中间没有任何库代码，清楚看到值在组件体内怎样流动。类似高阶组件的「装饰器 Hook」、类似 render props 的方案（如 adopt 提案、从 generator 里 yield）都有同样的问题；间接层也让静态类型更复杂。

    11

    结语：为变化而优化

    把这些方案摆在一起，「依赖调用顺序」换来了什么，又付出了什么？

    原文不求穷尽，还有些更晦涩的问题（比如与并发、高级编译技术相关）留待以后。Hooks 也不完美，有些事情还需要修，有些事用 Hooks 写比用类更别扭；但这是 React 团队能找到的解决这些问题的最好取舍。挑选 API 时考虑的标准，很多都和「为变化而优化」有关：确保复制粘贴、移动代码、增删依赖都按预期工作。[1][10]

    替代方案诊所（按原文归纳）：点一种方案，看它撞上哪个缺陷，再跳回对应章节。
    调用顺序看起来像个怪规则，但它让每一次调用都有自己的格子：自定义 Hook 可以随手提取、调用两次、互相嵌套、互相传值，代价是「只在顶层调用」这一条规则，以及一个帮你守住它的 linter。
