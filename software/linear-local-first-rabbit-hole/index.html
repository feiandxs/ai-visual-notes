Linear 与 local-first
    软件架构 · local-first · 同步引擎

    Linear 带我掉进了 local-first 的兔子洞

    一个项目管理工具快得不像网页：点开就有，改完另一个浏览器几乎同时变。作者顺着这个疑问挖下去，看到的是一种把数据库搬到浏览器里的架构，以及围绕它成长起来的一整个工具生态。

    把数据库放到客户端，读写都在本地完成，网络同步退到后台，网络延迟就从用户交互路径上消失了。代价是同步、冲突、权限、迁移这些难题全部摆上桌面，所以值不值得，要看你的应用是什么样的。[1]
    JJye Cusch

    原文：「Linear sent me down a local-first rabbit hole」，Jye Cusch，Bytemash（bytemash.net，2025-08-04），英文。本页按原文的叙述顺序翻译讲解，所有演示都是本页用 JS 做的模拟，不连接任何真实服务；另加了几处标注为「本页补充（非原文）」的核对与延伸。

    01

    网络延迟去哪儿了？

    在 Linear 里点开一个 issue 立刻打开，改个状态，另一个浏览器窗口几乎同时更新。没有加载状态，没有刷新。做了多年传统 Web 应用的作者觉得这「不对劲」：网络延迟哪去了？

    同一个操作，两种架构赛跑。拖动滑块设定网络往返时间（RTT），点按钮把 issue 的状态往前推一格。左边要等服务器回话，右边先写本地数据库、立刻重绘，再在后台把变更同步给「另一个浏览器」。原文结尾那句「在一个响应时间动辄 300ms 的世界里」，所以默认值设成 300ms。

    作者三问：网络延迟去哪了？冲突怎么处理？断网会怎样？后面几章依次回答。他也推荐先去看 LiveStore 的官方演示，感受一下 local-first 应用用起来是什么样子。

    02

    兔子洞底下：把数据库搬进浏览器

    一个下雨的周末、太多咖啡和几篇逆向分析之后，答案很短：Linear 自己写了一个同步引擎，把浏览器里的 IndexedDB 当成真正的数据库用。

    所有修改先在本地发生，然后在后台用 GraphQL 发送变更（mutation），用 WebSocket 接收同步。作者的资料清单包括：一份得到 Linear CTO 认可的同步引擎逆向工程、另一篇同步协议拆解、Linear CTO Tuomas Artman 的两场架构演讲，以及他在演讲中提到的 Figma 多人协作技术博客。[3][4][5]

    「local-first」这个词也反复出现。看你读的是哪篇，它要么是一种用户体验策略（让应用感觉像本地的：即时更新等），要么是一种理念（数据留在本地，在设备间同步）。多数情况下概念很简单：应用不再是「把数据发给服务器的高级表单」，而是自带一个本地数据库；有时服务器只是另一个需要同步的客户端。这可能是对 Web 应用常规做法的根本倒转。

    原文用两段文字图对比了两种数据流。切换模式，点「下一步」沿箭头走一遍：用户在等表示这一步卡在交互路径上，用户已看到表示界面已经更新，后台表示用户感觉不到。

    作者的关键收获：数据库搬到客户端，网络延迟就从用户交互路径上被拿掉了。更新之所以即时，是因为它们只是本地数据库的读写。

    本页补充（非原文）：「local-first software」一词的常见出处是 Ink & Switch 的 Kleppmann、Wiggins、van Hardenberg、McGranaghan 在 2019 年发表的同名文章，提出七条理想：快（不必等网络）、多设备、离线可用、协作、长期可用、隐私、用户掌控数据。原文所说的「理念」一派大体指这篇；「UX 策略」一派则更像 Linear 这种：服务器仍是权威，但客户端缓存了足够多的数据。[2]
    03

    难点：这一点也不简单

    看懂 Linear 的做法后，作者的第一反应是自己也写一个。随后现实来了：就算是基础版本的同步引擎，大概也要几个月的工程量。

    原文列出的复杂度来源：

    • 优雅地处理离线与在线切换下方模拟
    • 分布式客户端之间的冲突解决下方模拟
    • 部分同步：你不会想把整个数据库都下载下来见第 07 章 Shape
    • 缓存数据的 schema 迁移
    • 分布式系统里的安全与访问控制见第 05 章 Group
    一个最简同步引擎的模拟。两个浏览器编辑同一个 issue，中间是服务器的变更日志。每次修改立即写本地，再排队发给服务器；服务器给每条变更编一个递增的同步号，再广播给其他在线客户端。试试：先让 B「断网」，B 改状态，A 也改状态，再让 B 联网，看谁的值留下来。
    本页补充（非原文）：这个模拟用的是最朴素的规则：按字段「最后写入者胜」（last-writer-wins），先后以服务器收到的顺序为准。据原文引用的逆向分析，Linear 的同步也以服务器分配的递增同步 ID 为骨架，客户端记住自己见过的最后一个 ID，重连后补拉差量。[3] 更复杂的方案（如 Figma 博客里讨论过的 CRDT 思路）可以把并发修改合并而不是覆盖，但实现和存储成本都更高。[5]

    05

    深入 Jazz：像改本地状态一样写 local-first 应用

    作者先挑了 Jazz，因为它许下了一个离谱的承诺：构建 local-first 应用就像更新本地状态一样简单。

    Jazz 引入了「协作值」（Collaborative Values，CoValues）：为分布式实时协作设计的数据结构。你先用 Jazz 加 Zod 写 schema，但它们不只是类型定义，而是会自动同步的、活的响应式对象：

    // 用订阅 hook 取到一个值
const post = useCoState(Post, postId)

// 然后像普通对象一样用它
const setTitle = (title: string) => {
  post.title = title
  // 就这样。已经同步了。我没开玩笑。
}

    没有 API 路由，没有请求/响应循环，没有 DTO。作者说这「有点像作弊」。底层用了几个巧妙的办法：① 内置唯一性，每块数据自动分配唯一 ID，避免冲突、便于高效同步；② 事件溯源（event sourcing），变更看起来以事件形式存储，再物化出整个对象图的当前状态，同步时只传变更；③ 端到端加密，数据在客户端加密后才同步，服务器只看到密文；④ 用 Group 做权限，代替传统的 ACL。

    CoValue 演示。两台设备绑定同一个 post.title，在任一个输入框里打字，另一台会跟着变；下方是事件日志。再试「删除」和「撤销」，然后切到「服务器视角」，看看服务器到底能看见什么。
    Group 权限。原文示例：
    const group = Group.create()
group.addMember(alice, 'admin')
group.addMember(bob, 'writer')
Post.create({ title: "a new post" }, { owner: group })
    06

    取舍：服务器是瞎的，时间旅行是强制的

    这套架构做原型特别高效：不用每做一个交互就停下 UI，去写 API 和 DTO。但它也带来一些有意思的约束。

    服务器是瞎的

    一切端到端加密。除非通过 Group 明确共享给服务器账号，否则你的后端读不到用户数据。对隐私很棒；可要是没提前想好服务器需要访问哪些数据，就不那么棒了。想做内容审核、阻止恶意数据存储，也是问题。

    时间旅行是强制的

    Jazz 看起来用了事件溯源，每次修改都永久保存。那个「删除」按钮？只是移除了引用。做撤销重做很好，想到 GDPR 合规之类的事就没那么好了。

    存储只涨不跌

    既然什么都不删，存储用量只有一个方向：往上。小项目谁在乎；几千用户的 SaaS，AWS 账单可能长得像电话号码（或者等 Jazz Cloud 推出付费方案后，是它的账单）。

    本地开发仍有坑

    Jazz 应用默认展示的第一种登录方式是 Passkey。Passkey 有很多优点，但本地开发时很麻烦，见下面作者的十步折腾。

    本页补充（非原文）：GDPR 第 17 条规定了「删除权」（right to erasure，俗称被遗忘权）：数据主体在特定情形下可要求控制者删除其个人数据。在只追加（append-only）的事件日志里「删除」只是移除引用，原始事件还在，这就是原文说的合规顾虑。上一章演示里的「删除」也是这样做的。[7]
    作者的十步折腾：在笔记本上写了个小应用，想用局域网 IP 在手机上测。点「下一步」一步步回放。
    本页补充（非原文）：WebAuthn（Passkey 的底层标准）只在「安全上下文」中可用，即 HTTPS 页面，或被浏览器视为可信的 localhost。所以一换成 192.168.x.x 这样的局域网地址就必须上 HTTPS；而 HTTPS 页面里的 WebSocket 也必须是加密的 wss://，否则会被当作混合内容拦下，这就是第 8 步。[6]

    作者也注意到 Jazz 即将集成 Better Auth，能解决自托管场景的登录问题。他的结论：尽管有这些问题，依然值得。Jazz 非常惊艳、好玩，开发体验独特而高效；它还很早期，相信这些问题会有好的解法。

    07

    下一站：Electric SQL 与 Zero

    Jazz 从零造了一套新东西；Electric 和 Zero 走的是渐进路线：照常建 Postgres 表就行。

    -- 照常建 Postgres 表
CREATE TABLE posts (
  id SERIAL PRIMARY KEY,
  title VARCHAR(255) NOT NULL,
  content TEXT,
  author_id INTEGER NOT NULL
);

    Electric 用响应式查询返回数据库的子集，称为 Shape。下面这段建立一个订阅，之后表的变化都会被 Electric 同步到 UI：

    import { useShape } from '@electric-sql/react'
function Component() {
  const { data } = useShape({
    url: `http://localhost:3000/v1/shape`,
    params: { table: `posts` }
  })
  return <pre>{ JSON.stringify(data, null, 2) }</pre>
}
    Shape 与部分同步。左边是服务器上的 posts 表，右边是客户端订阅到的子集。换一个 Shape，再让服务器插入新行，看哪些会被推到客户端。最后试试在客户端改一行：Electric 与 Zero 的差别就在这里。

    Electric 能接现有 Postgres，很有吸引力；但还剩一个缺口：写入（mutation）怎么办？要得到 Jazz 那样的生产力，给 Electric 加上 LiveStore 看起来很有意思，不过它对 Postgres 的 schema 有特定要求；TanStack DB 也是候选，作者很快会试。Zero 则与 Electric 有很多相似之处，同时直接支持写入。最终选哪个，大概就是作者下一篇文章的主题。

    注：原文 SQL 在 author_id INTEGER NOT NULL, 后多了一个逗号，Postgres 会报语法错误；本页引用时去掉了。

    09

    展望

    local-first 代表了构建应用方式的一次根本转变。用户体验上的好处无可否认，Linear 已经证明了；问题在于这些架构取舍对你的场景值不值。

    作者正在用 Jazz 写一个个人应用，在实践中体会这些取舍：开发体验让人耳目一新，但他也在留意抽象会在哪里漏。生态还年轻，工具会成熟，模式会出现，棱角会被磨平。但核心洞见不会消失：把数据留在本地，可以做出好得多的用户体验。

    如果你在做新东西、又能接受这些约束，作者鼓励你试试 local-first。最坏的结果是学会一种新的架构模式；最好的结果是做出一个让用户觉得快得不可思议的东西。

    在一个响应时间动辄 300ms 的世界里，这就是优势。
