    暗网市场的安全模型

    一个在对抗环境里活了四年多的网站，怎样在不写一行 JavaScript 的前提下做验证码、防钓鱼、做双因素认证，又怎样处理「平台本身可能卷款跑路」这种普通网站很少需要面对的威胁。

    暗网市场平均只活八个月，原文考察的那家却从 2020 年 5 月运行到写作时。作者认为它靠的是一套层层设防的运营安全：没有 JavaScript、用验证码逼用户读防钓鱼提示、PGP 签名的镜像列表与 PGP 双因素、分层分配的私人镜像、薄托管与 Monero。它在保护用户隐私上做得很好，运营者自己的身份保护却未必。[1]
    EEvan Boehs

    原文：「The fascinating security model of dark web marketplaces」，Evan Boehs，boehs.org（2024-11-30）。本页按原文的叙述顺序做成中文讲解，并加了几处标注为「本页补充」的核对与延伸。

    阅读说明：原文作者明确说，写这篇是把它当作一个技术上的奇观来考察安全模型，不美化、也不评论市场出售的东西；原文隐去了站点名称与网址，本页同样不提供任何站点名称、地址或使用方法。页面里出现的地址、密钥、密文都是虚构的示意数据，签名校验也是用简单哈希模拟的，不是真实密码学。
    01

    短命的市场，和一场「进化」

    丝绸之路（Silk Road）倒下后需求没有消失，新市场来来去去。为什么偏偏有一家活得特别久？

    原文说，市场倒下无非三种原因：体面退出（clean exit）、执法打击、跑路骗局（exit scam，运营者卷走用户资金消失）。平均寿命只有八个月。这种兴衰循环带来一种「进化」：每个新市场都从前一个的漏洞里学习。原文考察的这家自 2020 年 5 月运行至今（指写作时），作者认为它的长寿和口碑来自格外出色的运营安全（operational security，opsec）。

    寿命对比：平均寿命取原文的「八个月」；这家市场的运行时长按 2020-05 到原文发表的 2024-11 现场计算。

    02

    一切从「没有 JavaScript」开始

    不能运行脚本的网页，怎么知道你在验证码图片上点了哪里？

    这个圈子坚持尽一切可能避开 JavaScript：它天生容易出漏洞，也给浏览器指纹（fingerprinting）留了很多口子，哪怕 Tor 已经尽力防范。网站必须在一行 JS 都没有的情况下功能完整，于是出现了不少有创意的写法。第一个例子就是验证码：服务器生成一张图，任务是「点进那个带缺口的圆」。

    可点的验证码：在图上点那个带缺口的圆。下方显示浏览器在没有 JS 的情况下会提交什么，以及服务器怎样凭会话里存的答案判断你对不对。图上方那句话模仿原文截图里的防钓鱼提示：做验证码的同时，你被迫读了一遍它。

    诀窍是一个少有人知的表单控件 <input type="image">（图像提交按钮）。它像 <input type="submit"> 一样，点一下就提交表单，但会额外带上点击位置的两个参数，形如 ?x=32&y=46。服务器借助 CSRF 令牌知道自己把那个开口圆放在哪，表单提交时就能核对你是否也知道。[1][2]

    本页补充（非原文）：按 HTML 规范，图像按钮若有 name 属性（比如 name="captcha"），提交的字段名是 captcha.x 与 captcha.y；没有 name 时就是原文截图里的 x、y。坐标以图片左上角为原点、按图片的 CSS 像素计。本页上面的演示为了跑在普通网页里用 JS 计算坐标，真实做法完全不需要脚本。[2]

    别的站点有别的玩法。一个用 <input type="range"> 滑块把图片挪到正确位置；作者觉得最厉害的一个，是把一串复选框叠放在完全相同的位置：勾选一个，它就隐藏、露出下一个；CSS 根据「当前勾到第几个」重新摆放图片。之后还要把图中被星号遮住的网址片段打出来，又是一道防钓鱼。

    纯 CSS 的多步验证码（本页重做的同类机制）：把箭头转到朝上。那个「旋转」按钮其实是四个叠在同一位置的 <label>，每个对应一个单选框；选中第 k 个时，CSS 只显示第 k+1 个标签，并按 :checked 旋转图片。这个小部件本身不含一行脚本，状态文字也是 CSS 的 content 生成的。
    #rot0:checked ~ … .l1 { display:inline-block }
#rot1:checked ~ … .cc-pic { transform:rotate(180deg) }
/* 提交表单时，服务器只看 name="rot" 的值 */

    作者的评价：这些验证码可能更不利于无障碍访问，防机器人的效果大概也更差，但它们是「不用 JavaScript 也能做出很酷的东西」的惊人例子，而其中的防钓鱼手法值得普通网站借鉴。[1]

    03

    认不出的网址，用签名来认

    洋葱地址是一长串随机字符，没法像 google.com 那样一眼认出。链接是真是假，怎么判断？

    镜像越多，这个问题越严重。解法是在验证码下方公布一份用 PGP 私钥签名的镜像列表；其他网站转贴这些镜像时，也连同签名一起贴出。只要签名始终能追溯到同一把钥匙，你就能知道手里的链接是真的。

    签名校验模拟：你已经在本地固定（pin）了市场公钥的指纹。点选一个来源，再点「验证」；也可以直接改文本框里的任意一个字符再验证。签名由简单哈希模拟，只演示逻辑。
    本页补充（非原文）：这套做法的安全性全押在「第一次拿到的公钥是对的」上，这和 SSH 首次连接时确认主机指纹是同一个问题（trust on first use）。所以原文强调的是「总是追溯到同一把钥匙」：多个互不相干的来源贴出同一个指纹，才让人比较放心。
    04

    登录：每一步都在逼你看一眼

    登录流程为什么要这么长？每一步各防一件什么事？

    登录流程步进：按顺序点「下一步」，或直接点上方的步骤。第 3、4 步可以动手试：解密一段挑战码、在一排框里找到你的用户名。

    原文特别指出 PGP 双因素有两个作用：和大多数 2FA 一样，确保只有私钥持有人能登录；同时也确保用户真的会用 GPG 工具，因为市场的通信本来就靠 PGP 加密。[1]

    05

    私人镜像：不同的人看到不同的门

    公开地址迟早会被冒充、被攻击。怎样让一扇门出事时，其余的门不受牵连？

    登录后，设置里有「私人镜像」。分层是这样的：公开镜像给还没注册的人，因为公开，风险最大；登录后的用户被分到一个池，拿到这个池自己的镜像地址，每个人只看得到分给自己的那个，其余私有地址因此受到保护；完成交易后，用户所在的池再升级，如此往复。作者说，这大概就是所谓的纵深防御（defense in depth）。[1][4]

    分层镜像模拟：每个圆点是一个用户（灰色是尚未注册的访客）。选一种事件，看哪些用户的入口受影响（红色）。

    作者还观察到两个迹象，说明不同地址可能真的托管在不同地方：调查期间网站遭到 DDoS，部分地址仍然可用；在一个镜像上拿到的两步验证，拿到另一个镜像上用会失败。

    06

    钱包：托管就是跑路的风险点

    市场的内置钱包充当托管（escrow）。可托管的钱，运营者随时可能卷走。怎么让「能卷走的钱」变少，甚至变成零？

    内置钱包看着就有风险，事实也是如此：开发者完全可以在一次跑路骗局里把钱包清空。据说这家市场做了些预防：下单、价格确定之后 3 小时内再付款即可，卖家也可以自动提现。这样托管钱包里就不会长期压着很多钱，作者称之为「相当薄」。（作者补了一句：他不打算通过下单来验证这两条说法。）

    托管风险模拟（示意模型，参数非原文数据）：把每天的成交额记为 1 份。拖动滑块，看「如果运营者此刻跑路，平台能卷走多少份钱」。中心化托管：买家习惯预存余额、货款压在托管里直到确认收货、卖家也不急着提现；薄托管：没有预存、卖家自动提现，只剩在途订单；多签：平台单方面一分也挪不动。

    更彻底的方案是加密货币的多重签名（multisig）：钱放在一个需要三方中任意两方同意才能动用的地址里，三方是买家、卖家和市场。这样的托管不怕跑路，但支持得不好，这家市场也没有采用。

    2-of-3 多签：点钥匙给交易签名，看这笔钱能不能被转走、这对应现实中的哪种情况。
    07

    别把秘密交给平台保管

    收货信息为什么要自己加密？为什么不用比特币？

    下单时，买家用卖家的公钥加密收货信息再发出。如果买家没加密，市场会用自己的密钥替你加密。原文说，依赖这一点「公认是个坏主意」：市场可以选择留存这些信息用来勒索，别的跑路骗局里就发生过这种事。

    谁能读到这段信息？切换两种做法，看信息在每一跳是明文还是密文，以及各方能否读到。

    和早期市场不同，这家不用比特币，而是围绕 Monero（门罗币）构建。它因匿名性很强而颇具争议。原文引用维基百科：「观察者无法辨认交易 Monero 的地址、交易金额、地址余额或交易历史。」[5]作者推荐数学背景的读者去读《Zero to Monero》，看基础数学如何做出技术上惊人的结果。[6]

    同一串交易，在两种账本上看到什么：切换账本，比较公开链上能看到的字段。数据为虚构。
    本页补充（非原文）：Monero 的三件主要工具：环签名把真实的花费来源混进一组诱饵里，观察者分不出是哪一个；隐身地址（stealth address）让每笔收款落到一次性地址上，公开地址不会出现在链上；RingCT 用承诺隐藏金额，同时仍可验证收支相等。详见《Zero to Monero》。原文作者另附一句：他觉得密码学（cryptography）很酷，加密货币（cryptocurrency）则无聊又烦人。[6]
    08

    运营者：网站很安全，身份不一定

    一个把用户隐私保护得很好的系统，它的运营者是否同样安全？

    原文这一节转述了运营者的背景与自述。与安全模型相关的要点如下（本页只做概括）：

    站点层面：做得很好

    管理员关注 Monero 追踪研究，自称「每一步都规划好，让我的匿名不只今天成立，十年后也成立」，并用一条内容安全策略（Content Security Policy，CSP）把「不执行 JavaScript」落到实处。作者从零碎线索判断后端用 Ruby（但不是 Rails），样式用 Tailwind。[1][3]

    Content-Security-Policy: script-src 'none'

    上面这一行是本页给出的典型写法示意，原文没有贴出该站的具体 CSP。

    身份层面：作者认为偏弱

    站点起源于欧洲；管理员接受过一家德国加密货币博客的采访，在论坛上高调发言，还夸耀曾入侵另一家市场（随后退款给那边的用户）以证明自己的安全能力。作者推测运营者或许把自己想象成殉道者，因此可能出现「把用户隐私保护得很扎实，却没保护好自己的隐私」的局面。作者也直言：为了证明安全能力去黑别的市场，很难让人觉得他们是好人。

    本页补充（非原文）：这一章说明了威胁模型的一条常识：系统的安全边界和人的安全边界是两回事。再严密的技术栈，也挡不住运营者在公开场合留下的语言习惯、作息、经历等线索。原文在「运营者」一节的推理就是在用这类线索（英语水平、论坛活动、采访平台、数字格式用小数点而非逗号）做画像。
    09

    没有 JavaScript，界面照样灵敏

    一个不能跑脚本的网站，侧边栏切换和弹窗是怎么做的？

    作者发现它的侧边栏导航「灵敏得惊人」，于是去翻了 CSS：侧边栏是一组单选按钮，CSS 选中当前被选的按钮，再把它的相邻兄弟显示出来。弹窗则用元素的 id 实现，即 :target 伪类。下面两个小部件都是纯 HTML + CSS，没有脚本。

    单选按钮侧边栏：点左侧条目切换右侧内容。
    选中的单选框 #rs1 让它后面的 label 高亮，再让 label 后面的面板显示。
    切换完全靠浏览器原生的「同组单选只能选一个」，CSS 负责显隐。
    缺点：状态不进网址，刷新后回到默认项；好处：零脚本、零指纹面。
    选择器：input:checked + label + .panel { display:block }
    :target 弹窗：链接指向一个 id，被指向的元素匹配 :target 而显示。
    打开弹窗
    <a href="#pop">打开</a>
<div id="pop" class="pop">…<a href="#">关闭</a></div>
.pop{display:none} .pop:target{display:flex}

    这个案例的可借鉴之处：把防钓鱼做成用户绕不过去的步骤，用签名而不是「看着眼熟」来认证地址，把公开入口和私有入口分层，尽量不替用户保管能被滥用的东西（资金和明文信息），以及在没有脚本的约束下，HTML 与 CSS 原生能力能走多远。
