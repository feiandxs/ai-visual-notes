    拆解 Cline 的系统提示词

    一个开源编程智能体，在每次对话开头先给模型塞一份约 4.8 万字符的「上岗说明书」。这页把它按段拆开：每一段写了什么、为什么这样写、哪些地方会随你的电脑和设置变化。

    Cline 的系统提示词就是一个 TypeScript 模板字符串：一句角色设定，接着用 ==== 分隔的八大段（工具与 XML 调用协议、MCP 服务器、编辑文件、ACT/PLAN 模式、能力、规则、系统信息、目标），末尾再拼上用户自己的指令。模型能做什么、怎么开口、什么时候停，全写在这里。[1]

    02

    四个参数：为什么每个人收到的提示词都不一样

    它不是一段写死的文本，而是一个函数 SYSTEM_PROMPT(cwd, supportsBrowserUse, mcpHub, browserSettings)。这四个参数改了哪些地方？

    参数注入器：切换操作系统、工作目录、是否支持浏览器、接了几个 MCP 服务器，看提示词里对应的句子怎么变。黄色高亮是被替换进去的值。
    本页补充（非原文）：系统信息段用到的 osName()、getShell()、os.homedir() 分别来自 npm 包 os-name、Cline 自己的 shell 工具函数和 Node.js 的 os 模块（见文件开头的 import）。注入器里的操作系统名、Shell 路径、视口尺寸只是示例值，不代表某台真实机器。cwd.toPosix() 会把 Windows 路径里的反斜杠换成正斜杠，所以 Windows 用户看到的也是 C:/… 形式。

    工具定义：模型手里有哪些「动作」

    TOOL USE 段占了全文一半。每个工具都按同一个模板写：Description、Parameters、Usage。它们各要哪些参数？

    工具参数查看器：点一个工具名，看它的中文说明、参数表（必填/可选）和提示词里给出的 XML 用法。虚线框的 browser_action 只在 supportsBrowserUse 为真时出现。

    04

    XML 调用协议：模型怎么「写」一次工具调用

    没有函数调用 API，模型只能输出文字。提示词规定：工具名做外层标签，每个参数各占一层标签，一条消息只能调一个工具，然后等结果。

    一次任务的消息往返：点「下一步」，看系统提示词、用户消息、模型回复依次出现；橙色框说明这一步受提示词里哪条规定约束。
    格式检查器：选一个预设或自己改文本框里的「模型回复」，按提示词里写明的几条硬规定逐条检查。这是本页按提示词条文写的演示，不是 Cline 真实的解析代码。
    本页补充（非原文）：工具结果以什么格式回给模型（例如往返演示里的 [read_file for '…'] Result: 和 <environment_details> 的具体内容）由 Cline 其他源码决定，不在 system.ts 里，演示中这部分标为「示意」。环境快照的内容和整个多轮循环，可看姊妹篇《Cline 是怎么工作的》。
    05

    编辑文件：为什么 SEARCH 必须逐字符一致

    提示词专门拿出一整段（EDITING FILES）讲两种写文件工具。默认用 replace_in_file，而它的 SEARCH 块必须是完整行、逐字符匹配，并且只替换第一次出现。这些规定各防什么错？

    SEARCH/REPLACE 匹配器：左边是一个小文件，选一个预设或自己改 SEARCH/REPLACE，看能不能匹配上、改了哪一行。判定严格按提示词的规则：SEARCH 的每一行都要和文件里连续的若干行完全相同，只替换第一处。
    write_to_file 还是 replace_in_file？提示词「Choosing the Appropriate Tool」的要点：

    replace_in_file（默认）

    小范围、局部的修改：改几行、换函数实现、改变量名；长文件里大部分内容不动的时候。原文称它「更安全、更精确」（Default to replace_in_file for most changes）。

    write_to_file

    新建文件；改动大到用 SEARCH/REPLACE 反而更复杂更易错；整体重组文件结构；文件很小且大部分内容要变；生成样板文件。要求给出文件完整的最终内容。

    另有一条容易忽略的提醒：编辑器可能在写入后自动格式化（换行、缩进、引号、import 排序、尾逗号……），工具返回的是格式化后的最终内容，下一次写 SEARCH 必须以它为准。

    06

    ACT 模式与 PLAN 模式

    同一份提示词里写了两种工作状态。模型怎么知道自己处在哪种模式，两种模式下能用的工具有什么不同？

    模式切换：切换模式，看工具清单里哪些被点亮。当前模式写在每条用户消息末尾的 environment_details 里，由用户手动切换。

    能力与规则：先说「你能做什么」，再说「你不准做什么」

    CAPABILITIES 段用散文告诉模型工具能组合出什么；RULES 段则是 20 多条硬性约束，篇幅仅次于工具定义。这些规则在防什么？

    规则分类浏览：原文 RULES 是一长串平铺的条目，本页把它们按用途分成四类，点分类筛选。每条附原文关键句。
    语气检查器：规则里有两条专管说话方式：消息不许以 "Great"、"Certainly"、"Okay"、"Sure" 开头；attempt_completion 的结果不许以提问或「还需要什么」收尾。在下面写一句回复试试。
    本页改写（非原文）：四个分类（环境、工具纪律、沟通、上下文）是本页为了阅读方便加的，原文没有分组；部分规则做了合并与节译。
    08

    系统信息与目标：每次调工具之前先想清楚什么

    SYSTEM INFORMATION 只有四行（系统、Shell、主目录、工作目录）；最后的 OBJECTIVE 把整件事归结为五步，第 3 步写了一套调用前的自检：参数不齐，宁可问也不要瞎填。

    调用前自检：选一个用户请求，点「下一步」，按 OBJECTIVE 第 3 步和 RULES 的要求一步步走到最终动作。
    OBJECTIVE 五步（节译）
    1. 分析任务，定下清晰可达的目标，并排好优先级。
    2. 按顺序推进，每次用一个工具，每个目标对应一个步骤。
    3. 调工具前先在 <thinking> 里分析：看文件结构、选最相关的工具、逐个检查必填参数；缺了且推断不出就别调用（「not even with fillers for the missing params」），改用 ask_followup_question；可选参数缺了不必问。
    4. 完成后用 attempt_completion 交付，可附一条演示命令（如 open index.html）。
    5. 用户可能给反馈，据此改进，但不要陷入无意义的来回，不以提问收尾。
    09

    用户自己的指令拼在哪里

    同一文件里还有第二个函数 addUserInstructions：它把用户的各种自定义规则按固定顺序拼成「USER'S CUSTOM INSTRUCTIONS」段，接在系统提示词后面。谁先谁后？

    拼接器：勾选你有的指令来源（括号里是示例内容），看最终拼出的尾段。顺序是代码写死的：偏好语言 → 设置里的自定义指令 → 全局 .clinerules → 项目 .clinerules → .clineignore 说明。

    原文这一段的引导语很讲究：用户指令要「尽力遵守」，但前提是「不干扰 TOOL USE 的规范」（without interfering with the TOOL USE guidelines）。也就是说，用户可以改风格、改偏好，但改不了 XML 调用协议。

    10

    一句话带走

    Cline 的「智能体能力」相当一部分写在这份提示词里：工具清单定义它能做什么，XML 协议定义它怎么说，「一次一个工具、等确认再走」定义节奏，RULES 管住边界和语气，OBJECTIVE 给出循环与自检，最后再留一个口子给用户自己的规则。

    从篇幅看，工具定义与示例约占一半，规则约占六分之一；角色设定只有一句话。写好一个智能体的提示词，重点不在「你是谁」，而在「你能做什么、怎么做、什么时候停」。
