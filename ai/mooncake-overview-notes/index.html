    关于 Mooncake 的碎碎念：给硬件厂商和云厂商的几条「暴论」

    Kimi 底层推理系统 Mooncake 发布技术报告的同一周，团队成员许欣然写了这篇短文：为什么 Prefill/Decoding 分离会是长期趋势，为什么要围绕 KVCache 做优化，以及集群和芯片现在该怎么准备。本页把每条论断拆成能拖、能点的小模型。

    只要自回归（AR）模型还是主流、KVCache 还这么大，decoding 的成本就和显存带宽强相关，prefill 则吃算力；而「算力/$」和「带宽/$」同时最优的芯片从没出现过，所以推理集群迟早要拆成异构的两半。[1]
    许许欣然（月之暗面 AI Infra）

    原文：「关于 Mooncake 的碎碎念」，许欣然，知乎专栏（编辑于 2024-06-28）。它与 ZHANG Mingxing（章明星）的「Mooncake (1)」「Mooncake (2)」属同一系列，那两篇讲架构细节，本篇是作者对行业的观点小结。本页忠实于原文的叙述顺序，并加了几处标注为「本页补充」的核对与延伸；页面里的数值模型均为示意，用于看清趋势，不是 Kimi 的真实数据。

    01

    一个先上线、后发论文的系统

    Mooncake 和那么多 Prefill/Decoding 分离的论文有什么不同？

    作者开篇说：这周把 Kimi 底层用的推理系统方案写成了一份简单的 Tech Report（开源在 GitHub 的 kvcache-ai/Mooncake）。团队坚信「一个系统方案只有实际在场景中验证过的，才有分享出来的必要性」。和很多 P/D 分离论文不同，这套方案已经在大规模集群上验证了几个月；这也是为什么一个 POC 写在所有业内论文之前的系统，直到现在才发布。

    > 80%Kimi 线上流量由这套系统承载
    数月大规模集群上的验证时长

    作者说，系统需要跟着应用快速变化，也需要硬件厂商和云厂商早点接受新理念才能跟上浪潮。发这篇论文，是想给各方一些信心，提供「推理规模足够大的场景下的必然优化思路」。

    02

    暴论一：分离策略是长期趋势

    同一个模型，为什么 prefill 和 decoding 要放到两拨机器上？

    作者给硬件厂商和云厂商的第一条「暴论」：Mooncake 这类分离策略会是一个长期趋势。他列了几条理由（原文列表层级按语义复原如下）：

    1. 1.1现在、立刻、马上真能省很多钱。「毕竟不能公开规模和每日请求的 pattern，如果你说省不了那你都对。」
    2. 1.2KVCache 的容量会长期保持高位，因此围绕 KVCache 来优化非常有必要。
    3. 1.3「private memory per request」是整个推理系统优化的关键瓶颈（否则 groq 万岁）。会有很多努力降低 KVCache 大小，但同时会有更多动力去增大它。
    4. 1.4分离之后，整个系统可以往「算力/$」和「带宽/$」两个方向独立发展，对硬件优化更友好：
      • AR 模型架构的惯性短期难以颠覆，所以 decoding 的成本总会和带宽成本强正相关；
      • 「带宽/$」低一个数量级的硬件方案已经在肉眼可见的范围内；
      • 纵观历史，「算力/$」和「带宽/$」同时最优的芯片似乎还没出现过，集群上必然要拆成异构的两部分。
    Roofline 小模型：切换阶段、拖动批大小和上下文长度，看每读 1 字节显存能做多少次计算（算术强度），以及它落在「屋脊」哪一侧。屋脊左边是带宽瓶颈，右边是算力瓶颈。
    本页补充（非原文）：模型取 70 亿参数、FP16 权重；硬件屋脊取「约 990 TFLOPS / 3.35 TB/s ≈ 296 FLOP/字节」，量级接近一张主流训练卡。为简化，忽略了注意力本身的计算量（对普通多头注意力约每字节 KV 1 次运算，不改变结论）。Prefill 一次处理整段提示词，几千个 token 共享同一份权重读取，强度轻松越过屋脊；decoding 每步每个请求只出 1 个 token，权重和 KVCache 都要整份读一遍，强度常常只有个位数到几十。两种负载放在同一张卡上，总有一边的资源闲着，这就是分离的出发点。[5]
    03

    Private memory per request

    「KVCache 容量会长期保持高位」，它到底有多大，又卡住了什么？

    暴论 1.2 和 1.3 说的是同一件事：每个请求都要在显存里占一块只属于自己的 KVCache（private memory per request），上下文越长占得越多。这块内存决定了一张卡能同时服务几个请求，也就决定了 decoding 能凑多大的 batch。作者说「否则 groq 万岁」：如果没有这块随请求增长的私有内存，把权重全放进片上 SRAM 的方案就能通吃了。

    显存账本：选一种注意力结构、拖动上下文长度与显存总量，看权重占掉多少、剩下的空间能装几个请求的 KVCache。
    本页补充（非原文）：每 token 的 KVCache 字节数 = 2（K 和 V）× 层数 × KV 头数 × 头维度 × 每元素字节数。三种配置按公开模型结构取近似值：MHA 类似 Llama-2-7B（32 层、32 个 KV 头、128 维）；GQA 类似 Llama-3-70B（80 层、8 个 KV 头）；MLA 类似 DeepSeek-V2（60 层，每层缓存 512 维潜向量 + 64 维 RoPE 分量）。[6] 关于 Groq：它的 LPU 主要依靠片上 SRAM 而非 HBM，SRAM 容量很小，装不下大量随请求增长的 KVCache，这正是作者那句括号的意思。
    04

    「算力/$」与「带宽/$」各走各的路

    为什么作者断言「集群上必然要拆分成异构的两个部分」？

    暴论 1.4 的逻辑链：decoding 成本跟带宽强相关（AR 惯性）→ 带宽便宜一个数量级的硬件快来了 → 但从没有一颗芯片在两项上同时最优 → 所以 prefill 交给「算力/$」最好的芯片，decoding 交给「带宽/$」最好的芯片。不分离，就只能挑一种芯片同时干两种活。

    采购账：两种假想芯片，A 算力便宜、B 带宽便宜。拖动负载里 prefill 的占比、B 芯片的「带宽/$」倍率，比较「全买 A」「全买 B」「分离后 A 管 prefill、B 管 decoding」三种方案的花费。
    本页补充（非原文）：这是一个只为说明结构的玩具模型，芯片参数是相对单位，不对应任何真实产品。它忽略了 P 与 D 之间传输 KVCache 的网络成本（Mooncake 论文里这部分靠 RDMA 与分布式缓存池解决）。评论区也有读者举例「Prefill 用 H100，Decoding 用 H20」，思路相同。
    05

    KVCache 变小了，Mooncake 还有用吗？

    MLA 和各种 KVCache 压缩方案，会不会让分离变得没必要？

    作者的第二条（原文编号 3）：Mooncake 方案和 MLA、各种 KVCache 压缩方案都是正交的，KVCache 变小意味着 Mooncake 的收益会更明显：同样的缓存池能存更多前缀，P 与 D 之间要搬的数据也更少。

    压缩倍率滑块：以 MHA-7B、32k 上下文、80 GB 显存为起点，把 KVCache 压缩 1× 到 1024×，看 decoding 能凑的 batch、此时的算术强度，以及每个请求要从 P 搬到 D 的数据量。

    评论区有人追问到了边界：

    读者 hzmzh
    「KVCache 变小了 Mooncake 方案收益会更明显」，如果 KVCache 小到 decode 都是 compute bound 了，是不是也没有 PD 分离的必要了？
    作者 许欣然
    确实，如果小到了这种地步那就是另外的 topic 了。

    在上面的滑块里把倍率拉到最大，就能看到这个「另外的 topic」：强度越过屋脊，decoding 也变成算力瓶颈。

    本页补充（非原文）：MLA（Multi-head Latent Attention）出自 DeepSeek-V2（2024 年 5 月），把每层的 K/V 压缩成一个低维潜向量缓存。[6] 注意本页模型里 batch 再大，decoding 的强度也有上限 ≈ 2×参数量 ÷（上下文长度 × 每 token KV 字节数），因为每个请求的 KV 都得单独读，没法在请求之间复用。压缩直接抬高的正是这个上限。
    06

    的确，有很多方向会让 Mooncake 变得没必要

    既然架构可能被颠覆，现在还值得为分离改集群、改芯片吗？

    作者的第三条（原文编号 4）很坦诚：确实有很多方向可能让 Mooncake 的架构变得没必要。但是：

    1. 4.1given hardware lottery，新架构演进会相当缓慢（不 AR、用 RAG 做 Attention 等方案），不能因噎废食。
    2. 4.2包括我们自己也在投入很多资源 break 现有框架，因此有理由相信在可见的未来推理方案还会变动。
    3. 4.3由于目前海量的推理压力，软件系统作为迭代速度极快的方案，就应该一代模型一次跟进。
    4. 4.4预测这个状态至少会持续 2~3 年，因此集群层面现在已经值得做拆分了。
    5. 4.5芯片层面值得作为一个重要的设计考量，在芯片的 IO 能力上要多预留一些。
    变数推演：点一个「可能的变数」，看它对分离架构意味着什么、按原文的思路该由哪一层（软件 / 集群 / 芯片）来应对。
    本页补充（非原文）：「hardware lottery（硬件彩票）」是 Sara Hooker 2020 年提出的说法：一个研究想法能否胜出，很大程度取决于它是否恰好适合当时已有的硬件和软件。[7] 套到这里：现有 GPU 和软件栈都为 Transformer + AR 优化过，新架构要先赢过这张「彩票」，所以替代会很慢。
