    Manus 的六条上下文工程法则

    把一个「GitHub 上看起来能跑」的智能体原型，变成扛得住百万次交互的系统，靠的往往不是更聪明的提示词，而是给模型搭一套稳定、可回溯、能自我纠错的上下文。这页把一条推文串里的六条拆解逐条做成可以动手试的小实验。

    Prompt 是告诉模型你想要什么；Context 是构建一个系统，让模型每一次都有机会自动靠近正确。[1]

    写在前面：智能体的成本花在哪里

    聊天机器人一问一答，输入输出大致均衡；智能体每一轮只输出几十个 token 的工具调用，却要读进几千上万 token 的上下文。

    作者说读 Manus 这篇博客，有当年读《编程珠玑》时「结构清晰又内功深厚」的感觉：很多坑大家都踩过，也做过优化，却没能把它总结成一条法则。拖动滑块看一轮「读上下文 + 推理 + 输出调用」里，输入和输出各占多少。
    本页补充（非原文）：Manus 博客给出的数字是，Manus 里平均输入与输出 token 比约为 100 : 1，一个典型任务平均要调用约 50 次工具；团队前后把智能体框架重写了四次，作者自嘲这套「搜架构、调提示词、凭经验猜」的过程叫「随机研究生下降」（Stochastic Graduate Descent）。[2]
    01

    法则一：围绕 KV-Cache 进行设计

    为什么系统提示开头的一个秒级时间戳，就能让整个智能体变慢、变贵？

    KV 缓存只认前缀：本轮请求与上一轮请求从头开始逐个 token 比对，一直相同的部分可以复用，从第一个不同的 token 起，后面全部要重新预填充（prefill）。下面两行是相邻两轮请求，打开上面任意一个「坏习惯」，看缓存从哪里断掉。
    Manus 的三条做法（推文串原文）：
    ① 保持提示词前缀稳定，哪怕一个 token 的变化也会让该位置之后的缓存全部失效；
    ② 上下文只追加（append-only），不改历史动作和观察，并保证序列化是确定的，很多语言序列化 JSON 时不保证键的顺序；
    ③ 显式标记缓存断点，有的推理框架需要手动插入，至少让系统提示末尾是一个断点。
    本页补充（非原文）：Manus 博客举的价格是 Claude Sonnet，缓存命中的输入 0.30 美元/百万 token，未命中 3 美元/百万 token，相差 10 倍（上面的费用即按此现场计算）。博客还建议自部署 vLLM 时打开前缀缓存（prefix caching），并用会话 ID 之类的办法把同一会话的请求稳定路由到同一批工作节点上，否则缓存在别的机器上也白搭。[2]
    02

    法则二：掩码，而非移除

    工具越来越多，为什么不该按需加载、中途增删工具，而是把它们全留着、在解码时「遮住」？

    切换策略和当前状态。移除：每换一个状态就改写上下文里的工具定义；掩码：工具定义一个字都不动，只在解码阶段用 logits 处理器屏蔽不允许的 token，或预填一段前缀。注意看历史里那条 browser_click 调用。

    推文串的总结：不要试图让模型「理解你不想让它做什么」，直接不给它做的可能性。工具名用统一前缀（浏览器类 browser_、命令行类 shell_），只允许某一类工具时，只要把前缀预填进去即可。

    本页补充（非原文）：Manus 博客以 Hermes 函数调用格式为例，区分三种模式：Auto（可调可不调，只预填回复前缀）、Required（必须调用某个工具但不限哪个，预填到工具调用标记为止）、Specified（必须从某个子集里选，预填到函数名开头，如 browser_）。统一前缀的好处是不用写有状态的 logits 处理器也能约束到一组工具。[2]

    法则三：将文件系统作为上下文

    上下文窗口给到 128K、1M 也不够用，那该扩容还是外置？

    点按钮让智能体遇到一个 2 万 token 的网页、几十页的 PDF、五层嵌套的 JSON。切到「外置到文件系统」后，大块内容写进文件，上下文里只留路径和一句摘要；需要时点右侧的文件把它读回来，用完再释放。

    推文串列出的三个问题：观察结果巨大，一次就可能撑爆窗口；即使没超限，超长上下文里模型表现也会下降；即使有前缀缓存，每个 token 的传输和预填充仍要付费。Manus 的回答是「不是扩容，而是外置」：文件系统大小不限、天然持久、智能体可以直接读写；而且压缩是可恢复的，网页正文丢了，URL 还在，随时能再读。作者把这称为让模型具备「知道信息在哪」的能力。

    本页补充（非原文）：Manus 博客原话是「我们的压缩策略总是设计成可恢复的」。博客结尾还设想，如果状态空间模型（SSM）学会把长期状态放进文件而不是放在上下文里，「智能体化的 SSM 可能成为神经图灵机真正的继承者」。[2]

    法则四：通过复述操控注意力

    走了几十步之后，智能体为什么会忘了自己最初要干什么？

    拖动滑块推进任务步数。不复述时，最初的目标一直停在上下文开头，离「最近的位置」越来越远；复述时，智能体每一轮都改写一份 todo.md、勾掉做完的项，把它贴到上下文末尾。条形长度是目标距离上下文末尾的 token 数（示意数值：每步约 1,500 token）。

    推文串的解读：这种「目标漂移」本质上是注意力失焦。LLM 的注意力更偏向上下文末尾的近期信息，复读把全局计划推进了模型的近期注意力范围，用自然语言本身偏置注意力，而不需要改任何模型结构。作者说它「特别美」：没有引入额外结构，却最接近人类不断自我提醒的行为。

    本页补充（非原文）：「迷失在中间」（lost in the middle）出自 Liu 等人 2023 年的研究：关键信息放在长上下文的开头或结尾时模型用得最好，放在中间时效果明显变差。Manus 博客用的正是这个词，说复述能避免它并减少目标错位。[2][3]
    05

    法则五：保留错误的内容

    出错就清掉重试，看起来「干净」，为什么反而让智能体永远不长记性？

    智能体要列出某目录里的文件，第一次调用写错了参数。选一种处理方式，反复点「下一轮」。关键看模型的输入：如果把失败抹掉，下一轮它看到的上下文和出错那一轮一模一样，凭什么会做出不同的选择？

    推文串：Manus 选择保留所有出错信息，失败调用、错误观察、甚至栈追踪，一条不删。有了这些证据，模型能在后续推理里隐式更新「信念」，降低在相似情境下重复犯错的概率。「错是它的，但学会是你的责任。」

    本页补充（非原文）：Manus 博客认为「错误恢复是真正智能体行为最清晰的标志之一」，并指出多数学术基准只测理想条件下的成功率，很少考察从失败中恢复的能力。[2]
    06

    法则六：不要被少样本示例所困

    上下文里的动作记录太整齐，为什么会把模型变成「照搬机器」？

    智能体在逐份审阅一批简历，历史里每一步的动作和观察都会成为它下一步的「示例」。切换序列化方式，看历史记录的模板相似度（页面现场计算相邻行的词重合度），以及它面对第 7 份「扫描件图片」时会怎么做。

    推文串：few-shot 用得太像「few-clone」，模型会陷入「格式安全区」，变成行动保守者而不是策略探索者。Manus 的做法是在动作和观察里有意引入少量但结构化的变体：语义一致、表达不同，让模型知道「还有别的方式也可以对」。

    本页补充（非原文）：「审阅一批简历时智能体容易进入节奏、重复相似动作」正是 Manus 博客自己举的例子；博客提到的变体手段包括不同的序列化模板、换一种措辞、顺序或格式上的小噪声。本页的「扫描件」情节为示意。[2]
    07

    最后：拿这份清单把你的系统过一遍

    所谓「智能体跑不起来」，往往是没给模型构造一个可持续运行的信息生命系统：记不清目标、摸不清状态、想不清下一步，更谈不上从失败中自我修正。

    推文串结尾留下的五个问题。按你自己的系统如实回答，下方会指出对应该回头看哪一条法则。
    六条约束一句话：前缀要稳，工具别动只遮，大块内容外置且可找回，目标每轮复述到末尾，错误留给模型看，示例要有变化。
