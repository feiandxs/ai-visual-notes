语义计算机中没有 Token
    可视化导读 · 公众号「孔某人的低维认知」 · 2025-01-23

    语义计算机中没有 Token

    副标题：正如 C 语言中没有寄存器。C 语言编译后的二进制代码会使用 CPU 寄存器，但 C 语言的层面没有寄存器的概念，也无法直接操作。

    作者的核心抽象：把 context 中的指令和过程当作语义程序，LLM 本身就是执行它的语义计算机。在语义空间里，token 和推理速度一样——是下面一层的事，感受不到。

    01

    回顾 Token：粒度太细，不是好的语义单元

    作者从 2023 年起反复提：LLM 的 Token 粒度不是表达语义的好方式，基于 Token 的学习方式对学语义来说效率也低。

    原文的例子：你并不是靠学「每个路口怎么打方向盘」来学会从北京开到广州的。切换视角，看同一段路程里的「决策单元」（示意）。
    • 但没找到更好的：一年半过去，仍未看到与 Token 不同、更接近语义粒度的建模方式。原因是没找到「更好地」表达语义的方式，而很多方案在和直接学 Token 的 scale 能力对比时没有显著提升，甚至下降。
    • 相关阅读（知乎）：《Rethinking LLM（1）：Token 与语义的 Gap》2023.5、《Rethinking LLM（3）：语义层面探索的一些想法》2023.6、《探索 LLM 的语义 loss 与模型设计（2）》2023.12。
    02

    现在的 Token：正在从 LLM 用户的心智中消失

    讨论 Token 问题的人本就不多，2024 年更少了——大家都觉得它够了。推理硬件和各种优化让 token 粒度过小对性能的影响不再那么大。

    三个时间点，作者自己对 prompt 的建议怎么变。上方的「token」会随之淡去。
    • 炼丹团队也一样：现在更在乎语料数据；对 Token 的关注多在一些特殊 Token 上，而那些与其说是 Token 层面，不如说是 Step / Message 层面的。
    03

    推理期计算 LLM：回答前先想一想

    本文把「明显会在回答前进行一个思考过程」的模型叫做推理期计算 LLM。从 o1-preview 到写作时已 4 个月，各方看法仍多样；作者对这个范式的评价却逐渐变高，这两天又跃升一次——这就是本文的写作契机。

    左：传统 LLM 直接从问题到答案。右：推理期计算 LLM 中间多了一段思考——探索、反思改错、切换思路（示意）。点「重播」再看一次。
    • 名字不好取：「推理 / reasoning」也不是好叫法——Anthropic CEO 最近说推理和 Agent 这个词一样，过于宽泛以至于几乎不提供信息量。MiniMax CEO 则表示还没看清 o 系列模型的未来，所以还没投入。
    • 两个主要价值（按重要性降序）：① 更好的分布外泛化能力，更能适应用户具体场景，同样效果下训练成本大幅下降；② 与现阶段高质量数据合成方式更匹配，总体训练成本更低，也更适合为具体场景特化模型（如 RFT）。
    04

    关键问题：可低成本获取的高质量数据【已经】几乎用完

    不是「快要用完」。什么算高质量也更清楚了：能进一步提升模型能力的数据才算。现在的前沿模型已很接近人类短时间思考的能力，大部分人类未经深思或没有专业加成的数据对提升没有帮助，甚至有害。

    左：数据「水位」。右：现阶段能大批量合成的两类高质量数据——数学（Lean 自动验证）和代码（沙盒执行测试）。自动验证的「质量」明显高于招大量专业人员撰写，成本也更低；前提是要有自动的结果验证工具。
    • 「污染」担心是多余的：即使没有 LLM 生成的内容，光凭人类数据也很难让模型进一步提升。模型可以从新数据中学到新信息，但能力没有提升。
    • 所以关键点是：如何构造能让模型能力进一步提升的数据。
    05

    AlphaZero 思路：让模型自己探索，而不是记住答案

    高质量人类专家数据不够多，质量也难说够高，所以很多研究者选择让模型自己探索出解决问题的方式。这种逐步探索的过程与推理期计算范式一致：学的是解决问题的方式，而不只是记住答案。

    左：没有思考过程的传统 LLM 更接近「直接记住探索的经验」——一个庞大的经验库。右：在新环境基于新信息重新分析问题——更有效的泛化，更能举一反三（示意）。
    • 代价转移：只是增加了推理期成本，而且由使用者承担，不必预先为不存在的用户投入巨大前置成本。
    • 不是新发现：在一些领域推理期计算早就是低成本优化效果的有效手段，Noam Brown 的学术生涯里做过不少（扑克到 Diplomacy）。相关阅读还有 Hyung Won Chung 的 MIT EI 讲座 "Don't teach. Incentivize."
    06

    如何训练：reward 在哪一级介入

    我们并不清楚 o1 怎么训练的。按 reward 信息的介入时间可以分三类：Token 级（value model，pretrain 和 SFT 也是这类）、Step 级（PRM）、整个回答之后（ORM）。

    一条回答被切成 token → step → 整体。点选一类，看 reward 挂在哪里，以及它的问题。
    • 流行趋势：直接用 ORM 做 RL，怎么解 prompt 完全靠模型自己探索。DeepSeek 的 GRPO 就是放弃了 value model。
    • LLM 并非从零开始：这与传统 RL 不同——pretrain 学了大量人类语料，会用人类常用的方式：反思思考历史、识别过去的错误、从一种思路跳到另一种……整个训练对模型的要求只是达到 reward model 的目标，方法不限。所以出现各种人类式思考模式并不奇怪，DeepSeek R1 报告里的 Aha moment 也属此列；也更能理解为什么 Apollo Research AI 安全报告里 o1 问题最大——它可能就是被这么训练的，「只要结果，方法不论」。
    • 作者的保留意见：并不觉得只能走完全没有结构和先验、只针对有完美 ORM 的领域。算力仍是瓶颈，不完美的 ORM 也有价值；某些问题里人工设计的 Step 和 PRM 仍有可取之处——5 年后可能不需要，但未来 2 年内可能很有用。
    07

    并非简单的 Policy Model：语义空间里的「A* 算法」

    只把 LLM 看成逐个生成 Token 的函数，它对应 RL 里的 policy model。但它还有两个能力：自我反思和改错、识别当前路径希望不大并跳到其他路径——这不符合传统 Policy Model 的认知。

    在语义空间里，LLM 包括：基于当前路径继续探索、反思改错、比较不同路径并适时切换……有点像一个 A* 算法并附带各种模型和策略（示意动画）。
    • 两个能力的来源：第二个能力看起来包含了 value model 或 PRM 的功能；第一个似乎没有传统对应物，因为一般的 RL 建模中没有犯错和改错。这两个能力不在 token 序列空间视角中，而在语义空间中。
    • in-context RL：虽然是在 token 空间训练的，LLM 似乎在语义空间学到了一种并不简单的探索能力。有人把推理期计算 LLM 算作 in-context RL，从这里确实能感觉到一些。
    08

    语义程序：把 in-context 空间当作语义空间

    回顾一下：想找更好的语义空间表示但没找到；推理期计算 LLM 在语义空间形成了某些能力；还有一些「in-context xxxx」的不明所以的叫法。到这里，就可以把 in-context 空间当作语义空间——只是其中的语义内容是非结构化的。

    以程序的角度审视那个「A* 算法」。三条性质：① 数据和代码不区分（很像 Lisp）；② 语义能力本身在 LLM 模型中，程序只是调用这些能力；③ 程序可以靠用户 prompt 注入，也可以在推理中从模型里提取，并对历史学到的程序片段进行融合组装。
    09

    可优化的语义计算机

    如果把 context 中的指令和过程当作程序和数据，那么 LLM 本身就是执行语义程序的语义计算机。它可以被优化——调整模型权重即可。

    点选一种信号，看它作用在哪一层。SFT 是固定语义程序、优化语义计算机；推理期计算 LLM 的 RL 训练则是计算机和它使用的程序的联合优化。目前的 RL 并不直接优化语义程序 / prompt，而是通过优化模型参数，影响程序的执行效果和执行中召回的程序。

    结语：不是新概念，但现在有了实感

    语义计算机至少在 2023 年就是一个常见想法。但作者觉得，到推理期计算 LLM 才让人更能获得一些实感——没有更适合的形容方式了。
