Mooncake：以 KVCache 为中心
    AI · 大模型推理系统

    在月之暗面做月饼：Kimi 以 KVCache 为中心的分离式推理架构

    Kimi 的推理平台 Mooncake 把一个同构 GPU 集群拆成 Prefill、Decode、KVCache 三个资源池。这一页带你走一遍请求的流程，再把作者讨论的几个「还没有共识的设计选择」逐个拿出来算一算、拖一拖。

    Prefill 管首字延迟（TTFT），Decode 管字间延迟（TBT），中间用一个跨机器的全局 KVCache 池做前缀复用。因为调度、分配、复制 KVCache 必须和 Prefill/Decode 的调度一起设计，作者把这套架构称为「以 KVCache 为中心」。[1]
    章ZHANG Mingxing（章明星），清华大学助理教授

    原文：《Mooncake (1)：在月之暗面做月饼，Kimi 以 KVCache 为中心的分离式推理架构》，ZHANG Mingxing，知乎专栏「KVCache.AI」（2024 年 6 月发布，2024-11-28 编辑）。作者在开头声明，文中「夹带过量私货个人观点，不代表本人单位更不代表 Moonshot，纯技术讨论」。本页按原文顺序讲解，加了几处标注为「本页补充」的核对与示意计算；所有示意模拟的参数都写在图旁，它们不是论文数据。

    01

    总体架构：一个集群拆成三个池

    一条请求进来之后，在 Prefill、KVCache、Decode 三个资源池之间是怎么走的？

    原文：Mooncake 是「非常典型的分离式架构，将单个同构 GPU 集群的资源打散并重新组织成三个可以独立弹性伸缩的资源池」。Prefill Pool 处理用户输入，对 TTFT（Time To First Token）负责；它相对计算密集，也承担着「抬高整体资源利用率」的任务。Prefill 算出的 KVCache 被送到 Decode Pool 做自回归（autoregression）式的流式输出，那里虽然也想攒大 batch 提升 MFU，但主要对 TBT（Time Between Tokens）负责。另外，每台 HGX 机器上的资源还组成一个 KVCache Pool，做全局的前缀缓存（Prefix Cache）。[1]

    点「下一步」，跟着一条请求走一遍。高亮的框是当前在干活的部分，流动的虚线是数据走向。步骤里的调度细节取自论文 [2]。
    本页补充（非原文）：论文里这个全局调度器叫 Conductor。它为每个请求算出 prompt 的分块哈希（block hash），查出每个 Prefill 实例已有的最长前缀，再按「排队时间 + 传输时间 + 剩余 Prefill 计算时间」估出 TTFT，选最小的那个；估出来超过 SLO 的请求直接拒绝。KVCache Pool 用的是 GPU 机器上原本闲置的 CPU、DRAM 和 SSD，机器之间通过 RDMA 传输。[2]
    02

    为什么用 TBT，而不是 TPOT

    两条回答的平均每 token 耗时一模一样，读起来的感受为什么会完全不同？

    原文：TBT 和 TPOT（Time Per Output Token）本来应该等价，但实际算 TPOT 时经常被简化成 average TPOT，也就是吞吐的倒数，或者总生成时间除以总 token 数。TBT 则明确指两个 token 之间的延迟，用 TBT 上限来定 SLO，更能反映流式交互的体验。作者的比方：如果 GPT-4o 的语音回复说一句、停一段、再说一句，「即便 average TPOT 能小一些，体验还是不够好」。[1]

    两路流式输出，总 token 数和总耗时相同，所以 average TPOT 相同。A 匀速吐字；B 一阵快一阵停。点「播放」看它们吐字，拖动 TBT 上限看各自有多少次「卡顿」超标。时间序列是本页的示意数据。
    03

    Prefill Pool：To Separate or Not, Is It a Question?

    Chunked Prefill 已经让 Prefill 和 Decode 的边界变模糊了，为什么还要单独的 Prefill 节点？

    作者原本想把论文这一章起名为「Prefill: To Separate or Not. Is it a Question?」。他的立场是：除非 prompt 特别短（短到可以直接塞进 decode 的 continuous batch 里提升 MFU 又不违反 TBT SLO），否则还是倾向于独立的 Prefill 节点。理由有两条。[1]

    理由一：VRAM occupation cost

    作者定义了 VRAM occupation cost：KVCache 大小 × 它在显存里停留的时间。用 chunked prefill 时，每个 chunk 都要和其他 decode 请求拼在一个 batch 里算，这会显著拉长这份 KVCache 在显存里停留的时间，等于降低了宝贵显存的利用率。（至于显存空出来有没有地方用，作者说是另一个问题，论文 4.2 节讨论了与未来 batch job 结合的可能。）[1]

    一个长 prompt 两种处理法。独立 Prefill 节点：整段一口气算完。Chunked prefill：每轮 decode 迭代只捎带一个 chunk，为了不让同 batch 的 decode 请求卡顿，这一轮的耗时得压在 TBT 上限以内。图里的矩形面积就是 VRAM occupation cost。参数是本页的示意值：Prefill 吞吐 20k tokens/s，纯 decode 一轮 30 ms，TBT 上限 100 ms，KVCache 按整段 prompt 一开始就预留。
    本页补充（非原文）：「一开始就预留完整 KVCache 空间」这个假设来自作者在评论区的回复：用 chunked prefill 处理特别长的 prompt，为了压低 TBT 要切成很细的 chunk，「说不定 chunk size 还得是个递减的」，因为历史越长每个 chunk 的计算量越大；而且得在处理第一个 chunk 时就预留好完整的 KVCache 空间，否则算到一半不够了换入换出很麻烦。结果是这份 KVCache 在 HBM 里留存时间比用独立 Prefill 节点长不少，间接让 decode 节点不好攒 batch。他也说这个界限是模糊的，未来可能按不同 TBT SLO 等级划分多个池。[1] 本图忽略了注意力计算随长度二次增长，所以低估了长 prompt 的差距。

    理由二：长文本要多节点并行压 TTFT

    更重要的理由：长文本场景下，Prefill 集群需要特殊的多节点划分来压低 TTFT。作者比较了被讨论更多的 SP（序列并行）和直接用 Chunked PP（分块流水线并行）的做法，认为后者在调度和减少通信量上更优：前者「大幅度简化架构」，后者「省出宝贵的传输带宽来搬运 KVCache」。具体做法是 TeraPipe 的推理简化版：只有 forward 没有 backward，不需要动态规划去平衡每个 chunk 的计算量，给每个 chunk 设一个最小值就行。[1][3]

    把 X 个节点串成一条流水线，每个节点负责模型的 1/X 层；prompt 切成 k 个 chunk，依次流过各节点。拖动两个滑块看 TTFT 怎么变。假设一个节点单独算完整个 prompt 要 8 秒，并忽略通信开销与注意力的二次项。
    本页补充（非原文）：论文把 Prefill 集群里每 X 个节点组成一个流水线组，每个请求按不超过 prefill_chunk 的长度切块，不同 chunk 可以同时在不同节点上处理；只有长度超过阈值（论文说「通常大于 1000 tokens」）的请求才分块。[2] 和 SP 的对比可以这样理解：流水线只在相邻两段之间传一次激活值；而 Ring Attention 这类序列并行，每一层的注意力都要在节点之间轮转交换 KV。[3][7]
    04

    KVCache Pool：从远端搬过来，比原地重算还快？

    全局 Prefix Cache 能成立的底层原因是什么？什么时候它会不成立？

    作者说「都 2024.6 了单节点的 Prefix Cache 已经不是什么新鲜东西了」，Mooncake 做的是全局的。相比 vLLM 当时的单机 Prefix Cache，全局调度能大幅提高复用率，从而提升总吞吐。[1]

    单机缓存 vs 全局池。同一串请求（30 篇不同文档做前缀，热度按 Zipf 分布）同时喂给两套系统。上：4 个 Prefill 节点各自缓存最近用过的 3 个前缀，请求轮询分配。下：4 个节点共享一个能放 12 个前缀的全局池。总缓存容量一样大。点按钮送请求，看命中率。这是本页的示意模拟。

    全局调度为什么划算？作者给的原理：对每 X 字节的 KVCache，生成它需要的算力正比于 X × hd × 一个较大的常数（hd 是模型的 hidden dimension）。所以只要每卡算力（比如 A100 的 220 TFLOPS）与每卡通信带宽（比如 CX7 的 100 Gbps）之比小于 hd 乘以这个常数，「从远端传输 KVCache 相比原地重算不仅仅减少了计算量还减少了 TTFT」。[1]

    选一个模型、调算力利用率和实际跑出来的带宽，比较每复用 1 个 token 的前缀：重算它要多久，从远端搬它的 KVCache 要多久。默认值就是原文举的 220 TFLOPS 与 100 Gbps。
    本页补充（非原文）：那个「常数」可以粗算出来。Prefill 每个 token 约需 2P 次浮点运算（P 为参数量）；KVCache 每个 token 占 2（K 和 V）× 层数 L × KV 维度 × 2 字节（BF16）。标准多头注意力的 Transformer 有 P ≈ 12·L·hd²，KV 维度 = hd，于是「算力 / 字节」≈ 24·L·hd² ÷ 4·L·hd = 6·hd；用 GQA 时 KV 维度缩小到 1/g，比值放大到 6·g·hd。上面计算器用的就是这个算法，只算了线性层，注意力那部分随前缀长度增加的计算没算进去，所以对「搬」是偏保守的。A100 的官方稠密 BF16 峰值是 312 TFLOPS，原文的 220 可以看作一个打了折扣的可用值。模型结构参数取自 Llama 2 论文。[4][5]

    但作者也强调这不是「一定可以」：hd 和常数都和模型结构强相关，只能说原则上比较大的模型应该都行；网卡虽然有 100 Gbps，如果 KVCache 下沉到慢速存储、或者网络拥挤，跑不到这么高，结论就不一定成立。所以需要以 KVCache 为中心，针对不同请求的 TTFT SLO 分别调度。论文 5.2 节给的是一个简单的、基于启发式的热点识别和复制方法：不需要预测未来的 KVCache 使用模式，好实现，实际效果不错，可以作为 strong baseline。[1]

    「第一次见这样的富裕仗」。作者感慨：标准 8 卡 HGX 服务器每台配 9~10 张 100 Gbps 乃至 200 Gbps 的 RDMA 网卡、至少 2 TB 内存和一堆高速 SSD，一千台就是「近万张网卡互连起来的数 PB 共享内存池」。拖动机器数，按原文给的下限现场算。[1]

    作者补了一句：可惜这是 bandwidth bound 的场景，架构上没那么多「奇淫技巧」可用，更多是工程实现。

    05

    Decode Pool：还能不能再拆一刀

    Decode 阶段里，为什么 attention 和线性层适合放在不同的硬件上？

    Decode Pool 是业界实践最多的部分，vLLM 迭代极快，「该有的不是已经有了也是在 roadmap 里」。作者在这里夹带的私货是论文 future work 里的想法：加入面向大容量、大带宽设计的高性价比设备，组成异构集群。他也坦白担心：硬件迭代慢，等出来了算法变了（比如 MLA），或者被「老黄的大力出奇迹创飞了」就很尴尬。[1]

    他还提到几个月前挂出的另一篇论文：不必等新硬件，组合基于 GDDR 的设备就能把 Decode 再拆成 attention 算子和 Linear 算子两个池子。[1][6]

    算术强度（每读 1 字节做多少次运算）决定一个算子吃算力还是吃带宽。拖动 batch 大小：线性层的权重被整个 batch 共享，强度随 batch 上升；attention 读的是每个请求自己的 KVCache，batch 再大强度也不涨。虚线是 A100/A800 的「拐点」：低于它就是带宽受限。
    本页补充（非原文）：上图按 BF16 粗算：线性层每个 token 每个参数做 2 次运算，权重每参数读 2 字节，所以强度 ≈ batch 大小；attention 对长度 n 的上下文做约 4·n·hd 次运算、读约 4·n·(hd/g) 字节，强度 ≈ GQA 分组数 g，与 batch 无关。拐点 ≈ 312 TFLOPS ÷ 2.0 TB/s ≈ 153 FLOP/字节（A100/A800 80GB 的公开规格）。这就是许欣然在同期文章里说的「private memory per request 是整个推理系统优化中的关键瓶颈」：attention 部分天然适合交给「带宽/$」更高的设备。[6][8]

    现实的阻碍：云上的 GDDR 设备一般不和旗舰显卡集群放在一起，为省成本只配很差的 CPU 和网卡；现有设备不是为这个场景设计的，attention offload 的性价比潜力发挥不出来，为此把架构变复杂、还增加一点 TBT，不一定合适。「所以归根结底还是得看看有没有硬件厂商愿意赌一把了。」[1]

    一句话回顾：把 TTFT 交给 Prefill 池、TBT 交给 Decode 池，用一个跨机器的 KVCache 池把「算过的东西」存下来、搬过去复用。只要搬比算快，又省钱、体验又好。
