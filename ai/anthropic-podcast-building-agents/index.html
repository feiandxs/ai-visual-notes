构建高效 Claude 智能体

    用代码、MCP、Skills
    构建高效 Claude 智能体

    Alex Albert（Claude 关系负责人）与 Erik Schluntz（多智能体研究员）的对谈，拆成 11 个画面。每节一个核心想法，用图和动画代替长文。

    三句话：编码是智能体最核心的技能；从最简单的方案开始，按需加复杂度；工具应映射 UI，而非 API。
    来源：Anthropic 播客（2025 年），中文整理：是莫尔索 · 莫尔索随笔，2025-11-04 · 本页为教学改编，标注“示意”的流程与数字仅用于说明。
    01

    Claude 为什么擅长当智能体？

    答案是大量的刻意练习：在强化学习中反复处理开放式问题，而且“先训练最难的东西”，也就是编码。

    训练时的循环：面对开放式问题，必须多步骤、用工具、探索环境，然后才给答案。
    编码能力的“溢出效应”：一个出色的编码智能体，几乎能用写代码的方式完成其他任何工作。
    • 外界常误以为编码能力“仅限技术领域、无法迁移”。Eric 的看法相反：编码是最基本、最核心的技能。
    • 搜索任务 → 写代码调用 Web 搜索 API；规划周末行程 → 写代码建一个日程表或数据结构。
    • Claude.ai 网页版的新功能就是例子：要一个表格，Claude 先写一段 Python，脚本跑完，Excel 文件真的出现在你面前。
    02

    让它写代码来生产产物，而不是直接生成产物

    Eric 的亲身经历：复杂图表，Claude 不再逐行写 SVG，而是写一段脚本去生成那个 SVG。

    点“开始”看两种做法赛跑。左：逐字生成冗长、重复的 SVG 文件；右：写一段短脚本，运行，产物瞬间出来。示意动画。
    • 简单图表时，Claude 直接写 SVG 没问题；一旦细节大量重复，它自己就换了策略。
    • 原则：对于复杂或重复性的任务，让智能体写代码来生产“人工产物”（artifact），比让它直接创建产物高效得多。
    03

    别重复造轮子：Claude Code SDK

    从零只靠 API 端点造智能体，意味着自己写循环、工具、执行、文件系统、MCP 处理。SDK 把这些全部打包了。

    下层是 Anthropic 已经打磨好的“核心智能体循环”；上层的插槽才是你该花时间的地方。点击插槽看例子。
    • 名字里有 “Code”，但 Claude Code 本质上是一个通用智能体，只是最常被用来处理代码任务。
    • 高度可定制：移除编码专用的部分，像插槽一样填入自己的 prompt 或工具。
    • Eric “最奇怪的用法”：接上网络搜索，用它规划了一次约会，推荐了长木花园（Longwood Gardens）和附近一家中餐馆，效果还不错。
    04

    Skills：从“给指令”到“给资源”

    Claude.md 只能放纯文本的笔记和指令；Skills 允许你把任何类型的文件作为“资源”交给 Claude。

    开发者工具层的演进，进入视口时逐级点亮。
    Alex 的比喻：《黑客帝国》里 Neo 被“注入”功夫。给 Claude 一个“如何创建电子表格”的技能包，它突然就像个能建财务模型的银行家。
    • 资源可以是：模板文件（公司官方 PPT 模板）、辅助脚本（现成的 helper scripts）、资产文件（图像、Logo，甚至全体高管的大头照）。
    • 以前只能说“做 PPT 要遵循公司规范”；现在把模板和照片直接给它，需要时“手头就有一切所需”。
    • Eric 的补充：这也像电影里“加载整个武器架”。技能不仅是知识，更是随时可取用的装备和工具。
    05

    从“链接提示”到“链接智能体”

    智能体循环已基本取代静态工作流，因为 Claude 很会响应反馈、纠正自己。最新趋势叫“智能体工作流”（workflows of agents）。

    同一个任务：先查数据库，再画图。切换“旧工作流 / 智能体工作流”，点“运行”看 SQL 出错时会发生什么。
    • 旧工作流：每一步都是单次尝试。步骤一的 SQL 失败了，步骤二一无所知，拿着错误或空的数据继续画图，整个流程“彻底搞砸”。
    • 智能体工作流：步骤一本身是一个完整的智能体，写 SQL、运行、看输出，不对就迭代，直到确认拿到正确数据，才把控制权交给下一步。
    • 工作流仍有价值：需要极低延迟、只要“一次性”答案的场景。
    06

    多智能体 ≠ 智能体工作流

    智能体工作流是串行的；多智能体是并行的，多个 Claude 实例同时工作。

    两种典型用法。切换查看：并行委托（更快拿到答案）与保护上下文（主智能体不被中间信息淹没）。token 数为示意。
    • 并行委托：Anthropic 内部的深度研究搜索产品，协调器智能体创建几个子智能体同时搜索。
    • 保护上下文：在庞大代码库里找某个类的实现要消耗数万 token，但答案只是“文件名 + 行号”。外包给子智能体，主智能体只收那一行。
    • 实现上复用了工具调用框架：子智能体对主智能体来说就是一个普通工具，prompt 作为参数传进去。
    • Claude 会犯和人类新手管理者一样的错：指令含糊，却默认下属知道自己的背景。训练后它变得更啰嗦、更详细，会主动交代“整体背景”。
    07

    最佳实践一：保持简单，按需增加复杂性

    永远从最简单的方法开始，只在绝对必要时加一层。每加一层，可观测性就更难。

    决策阶梯：从上往下，只有上一层确实不够用，才走到下一层。右侧是可观测性难度。
    • 今天的模型比一年前强得多，能撑住更复杂的设置，但原则没变。
    • 顺序：单次调用 → 封装好的智能体循环（如 Claude Code SDK）→ 智能体工作流 / 多智能体。
    08

    最佳实践二：站在智能体的立场上

    我们能看到一切，模型只看得到我们展示给它的东西。去读它看到的原始日志。

    切换视角。问自己：“如果我是智能体，只看得到这些，信息够解决问题吗？”
    • 给 Claude 任何工具、提示或功能（affordances）时，都要“设身处地站在 Claude 的立场上”。
    • 最有效的做法：阅读原始日志（raw transcript），看它在工具调用里实际收到了什么。
    09

    最佳实践三（核心）：工具应映射 UI，而非 API

    最常见也最严重的错误直觉：让工具和后端 API 一一对应。正确心智：和用户界面一一对应，因为模型是工具的“用户”。

    Eric 的 Slack 例子。点“让智能体理解这段对话”，数一数两边各需要几次工具调用。
    • 后端有三个端点：加载对话（只返回 user ID 和 channel ID）、ID 转用户名、ID 转频道名。按 API 映射，智能体理解任何事都要连续三次工具调用。
    • 人类看 Slack 看到的是“所有内容都已完美渲染好”的界面，不用点用户 ID 去看名字。
    • 所以：做一个工具，后台自己完成那三次 API 调用，一次性返回渲染好的完整对话。不要让智能体做连你自己都觉得“糟糕透顶”的繁琐操作。
    10

    未来 6 到 12 个月：自己封闭测试循环

    智能体会先在可验证的领域普及，比如软件工程。最大的增益点是自我验证。

    今天：写完代码，人类来当 QA 工程师。未来：智能体自己打开、测试、找到自己的 Bug。
    关键是把软件工程能力和“计算机使用”结合。例子：帮我清理一篇 Google Doc。
    • 一旦智能体能像人一样操作计算机（滚动、点击、编辑文本），大量目前“被拒之门外”的领域会被解锁。
    • 愿景：“无论你在哪里，Claude 都能与你同在。”
